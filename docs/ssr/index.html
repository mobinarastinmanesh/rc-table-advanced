SSR and Next.js

The ESM and CommonJS entries can render a table with react-dom/server. DOM work is deferred to client effects. Open modal/drawer primitives return no markup on the server and mount their portals on the client. URL filters are read after mount to keep initial markup deterministic.

Next.js App Router

Import the stylesheet in your root layout:

import 'rc-table-advanced/styles.css';
export default function RootLayout({
  children,
}: {
  children: React.ReactNode;
}) {
  return (
    <html lang="en">
      <body>{children}</body>
    </html>
  );
}

Define the interactive table, columns with render callbacks, and state in a client component:

'use client';
import { AdvancedTable } from 'rc-table-advanced/core';
export function OrdersTable() {
  return (
    <AdvancedTable
      rowKey="id"
      columns={[{ title: 'Name', dataIndex: 'name' }]}
      data={[{ id: 1, name: 'Jane' }]}
      hasSearch={false}
      hasSort={false}
    />
  );
}

The built JavaScript entries retain a use client directive. Application callbacks and column render functions must still respect the server/client boundary. Use your framework router as a controlled URL adapter if it does not emit browser popstate events.

Plain React SSR

Use the core entry and a stylesheet link generated by your bundler. Supply identical initial rows, filters and pagination on server and client. Fetch initial data in the application. URL-driven state can request a different page after hydration; show a loading state while that request completes.

CommonJS uses a real .cjs entry with separate .d.cts declarations; ESM uses .js and .d.ts. The package consumer check renders a real table through both formats and compiles consumer TypeScript with NodeNext and bundler resolution.

The checked-in fixtures/next application is built in production mode by npm run test:next. Browser tests also check hydration and interactive filtering in that fixture.
